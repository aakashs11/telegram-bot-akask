# Supabase migration

Reference for how the Telegram bot's Google Sheet data moved to Postgres. Production still reads Sheets until the flags below are changed. Merging this branch does not point Cloud Run at Supabase.

## What moved

| Data | Where it lives now | What did not move |
| --- | --- | --- |
| Student profiles | `students` | The two rows whose subject was Computer Vision or Banking |
| Notes catalog | `content_items` and `folders` | The PDF files. They stay in Google Drive |
| Group warnings | `warnings`, one row per student per chat | |
| New interaction logs | `interaction_events`, only after the log flag is turned on | The old Logs sheet. It stays the archive |

YouTube search is unchanged. The bot does not use the Supabase client library. It connects with a normal Postgres URL.

## How it was done

The work is on `feat/platformization/supabase-migration`. Two flags keep production on Sheets:

- `INTERACTION_LOG_MODE` defaults to `sheet`. `dual` writes each new message to the sheet and to Postgres. `postgres` writes only to Postgres.
- `BOT_DATA_STORE` defaults to `sheet`. `postgres` reads profiles, the catalog, folder links, and warnings from Postgres.

Schema changes are Alembic revisions `20260922_0001` through `20261013_0006`. Student and warning ids are the Telegram ids. They are not generated by the database.

Copy scripts read the sheets and upsert. Dry-run is the default. `scripts/sync_catalog.py` refreshes the catalog from Drive. It does not rewrite the Index or Folders sheets.

The first database is a Supabase Free project in Mumbai. This PC cannot reach the direct database host because that host is IPv6-only, so migrations and dumps use the session pooler on port 5432. Cloud Run should later use the transaction pooler on port 6543, stored in Secret Manager as `database-url`. The dev `.env` stays on local Docker.

A weekly dump is `scripts/backup_postgres.py`. It dumps only the `public` schema. `--restore-drill` checks the archive in a temporary database and then deletes that database. Supabase Free has no automatic backups. A schedule is not installed yet.

## What a student notices

With both flags left at `sheet`, private chat, notes, videos, and group moderation follow the same path as before, with three exceptions already on this branch:

- A student who already has class and subject saved is no longer asked for them again on a bare request such as "notes".
- "Sample Question Papers" matches the Drive folders named "Sample Question Papers SQP".
- An anonymous group-admin post, the Telegram user that posts as the group itself, is not moderated. A post that only reuses that user id is still moderated.

Log writes happen after the reply is sent. They do not add to the time the student waits, up to a 5 second cap if a sink is slow.

## Latency from this PC

Measured 16 Oct 2026 from this computer, which is far from Mumbai. Cloud Run is in `asia-south1`, next to the database, so production round trips will be much smaller than the Supabase numbers below. Both stores cache the notes catalog after the first read in a process, so later "notes" replies do not wait on either one. Log writes happen after the reply.

## Checks already done

On 16 Oct 2026 the Mumbai database was at revision `20261013_0006` with 1,900 profiles, 222 files, 93 folders, and 163 warnings. `interaction_events` had no old rows. A restore drill matched those counts.

One private "Give me notes" then wrote event `ec737deb-05e0-497b-b936-12b5df0c31fc` to Supabase. The Logs sheet rejected the same row because the worksheet only had columns A–G. Column H, `Event ID`, was added, and that row is sheet row 5659. The writer now adds the column when it is missing.

## Before production uses Postgres

1. Bring in `main` commit `bf40720` if it is not already contained. It is the same anonymous-admin rule, written against the old group handler.
2. Open the pull request. A push to `main` deploys Cloud Run. The workflow does not set the two flags, and the code defaults stay `sheet`.
3. Do not put the Supabase URL in Secret Manager until a dual-log day is planned.
4. At cutover, copy profiles and warnings again, run the Drive sync again, then dual-write new logs for a few busy days.
5. Turn `BOT_DATA_STORE` to `postgres` only after that compare. Schedule the five-minute Drive sync after the secret exists. The dev install does not have the Telegram job-queue package, so that job does not schedule there.
